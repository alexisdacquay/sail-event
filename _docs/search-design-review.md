# Search and scoring v2 — review

Reviewer had no part in the spec or the design. Reference case: C1 `jazz in Berlin (Germany) next week (19-21st October 2026)`, run 2026-10-18 (a Sunday), `Europe/Berlin`.
Provider and model facts below were checked on 2026-10-18 against docs.tavily.com (search endpoint, credits), api-dashboard.search.brave.com (web search query), api-docs.deepseek.com (pricing, JSON mode). "unverified" = the public page did not say.

## 0. The Portland event, traced

- Prod has no keys: `SEARCH_PROVIDER` unset → `FixtureSearchProvider` (`adapters/fixtures.json`, row 1 is "Outdoor Photography Meetup, Riverside Park, Portland"); `SCORER` unset → `FakeScorer` = `md5(title) % 101`. The Berlin criteria never reached a search engine or a model. The deployed result is a config state, not a scoring defect.
- v2 as written fixes it only through two things: keys set on Render and the prod refusal of fixture/fake. Everything else in the design is about quality once real adapters run. Both documents say this implicitly (spec §2 last line, design §12 row "Production refuses fixture") but neither says it first.

## 2. Cost

Assumptions: extraction ≈ 4 000 in / 250 out tokens (2 000 static prefix + 8 000 chars); judge ≈ 1 600 / 80; criteria ≈ 800 / 150 once. Spec's own funnel: 36 results → 12 events → 10 judged. Hourly warm: 2 queries → 12 results, 3 new pages typical, 12 worst. DeepSeek flash peak $0.30/M in (miss), $0.006/M cache hit, $1.20/M out; off-peak half. Latency per model call assumed 3–6 s (unverified).

| Case | Search calls | LLM calls | Tokens in / out | $ per run (peak) | Wall time |
|---|---|---|---|---|---|
| Manual, 1 user, cold | 6 | 1 + 36 + 10 = 47 | 161k / 10k | 0.06 (0.03 with prefix cache) | 3–5 min |
| Hourly, 1 user, typical / worst | 2 | 4 / 16 | 14k / 1k — 54k / 4k | 0.005 / 0.02 | 30 / 95 s |
| Per user per day, hourly | 48 | 96–384 | 0.3–1.3M | 0.12–0.50 | — |
| 50 users per hour | 100 | 200–800 | 0.7–2.7M | 0.25–1.0 | 25–80 min |
| 50 users per day vs caps | 2 400 vs **500** | 4 800–19 200 vs **3 000** | — | 6–24 | — |

- Search cap 500/day is hit after ~250 runs ≈ 5 hours of the day at 50 users; LLM cap 3 000 after 4–15 hours. The caps are sized for ~10 users, not 50; say so or raise them.
- Tavily free tier 1 000 credits/month: one user alone uses 1 440/month on the hourly schedule.
- Hourly 5-minute timeout: does not survive beyond 3–10 users (F5).

## 3. Rollout order

1. Today, on current code: set on Render prod `LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `TAVILY_API_KEY` (ignored by the old factory, harmless). Do not set `SEARCH_PROVIDER=tavily` yet: old code would search for real and score with `md5(title)`.
2. Issues A–E merge with the old pipeline intact (F4); dev keeps running fixtures + fake with `FAKE_NOW` (F3).
3. Issue F: swap; the prod refusal is at first use (F6); promote; then set `SEARCH_PROVIDER=tavily` and `LLM_JSON_MODE=json_object`; run the smoke on C1; only then enable the hourly job for prod (F5 shipped in G or before).
4. Issue G, then H. README screenshots after H, from dev with `FAKE_NOW`.

Sizing: A, C, D, E, G are one session each. B is one if the Anthropic adapter is dropped for now (owner is on DeepSeek; keep the Protocol, add Anthropic when needed). F is two: F1 judge + caps + golden B, F2 pipeline wiring + smoke + deletions. H is one.

## 4. Verdict

REWORK — the design would fail the Berlin case at its first stage (F1), lose every event added to a page it has already seen (F2), and break CI, the demo and prod start-up in ways the issue order does not survive (F3, F4, F6); each is a small change, none is optional.
Strongest fact against: the pipeline shape (code filters on extracted facts, judge with caps, budgets as reported outcomes) is right and none of the blockers touches it; a reviewer who weighted structure over the six concrete failures would say APPROVE WITH CHANGES.
